# Pi-only v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a source-installed Go `pbt` CLI that verifies required
Hypothesis/pytest properties and a thin Pi extension that enforces the CLI gate
at completed-turn settlement.

**Architecture:** The Go CLI owns configuration, contracts, task state,
fingerprints, subprocess execution, pytest evidence, retry decisions, and gate
results. The Pi extension only detects an active task, injects concise policy,
and maps the CLI gate JSON to Pi's `agent_before_settle` continuation result.

**Tech Stack:** Go 1.24 standard library; Python pytest and Hypothesis in a
fixture; embedded Python pytest plugin; Pi extension TypeScript; Node 24 for
extension contract tests.

**Spec:** `docs/superpowers/specs/2026-09-17-pi-only-v1-design.md`

## Global Constraints

- V1 supports exactly one active task, one Python project root, and one
  argument-array property-test command per worktree.
- `pbt` uses no Go third-party dependencies and never executes a shell string.
- `pbt.config.json`, contracts, and configured input globs determine freshness.
- `.pbt/contracts/` is reviewable and committed; `.pbt/state/` and `.pbt/runs/`
  are local operational data and must be Git-ignored.
- Required contract node IDs must be collected and must pass according to the
  bundled pytest reporter's JSONL. JUnit is retained as a human artifact only.
- Pi creates a continuation only from `agent_before_settle` with
  `outcome === "completed"`; abort and error outcomes never auto-continue.
- A task gets at most three automatically dispatched corrective follow-ups.
- Do not add Claude Code integration, Pi tools/slash commands, workers,
  multi-package selection, documentation fetching, or release-binary packaging.

## Shared interfaces

All Go tasks use these names and JSON values:

```go
// internal/core/types.go
type VerificationState string
const (
    VerificationPending       VerificationState = "pending"
    VerificationRunning       VerificationState = "running"
    VerificationPassed        VerificationState = "passed"
    VerificationFailed        VerificationState = "failed"
    VerificationStale         VerificationState = "stale"
    VerificationNotApplicable VerificationState = "not_applicable"
)

type WorkflowState string
const (
    WorkflowActive    WorkflowState = "active"
    WorkflowComplete  WorkflowState = "complete"
    WorkflowBlocked   WorkflowState = "blocked"
    WorkflowCancelled WorkflowState = "cancelled"
)

type Result struct {
    SchemaVersion     int               `json:"schemaVersion"`
    Task              string            `json:"task"`
    VerificationState VerificationState `json:"verificationState"`
    WorkflowState     WorkflowState     `json:"workflowState"`
    ReasonCode        string            `json:"reasonCode"`
    NextAction        string            `json:"nextAction"`
    FollowUp          string            `json:"followUp,omitempty"`
}
```

The CLI prints exactly one `Result` JSON value to stdout when `--json` is set.
Diagnostics and subprocess output summaries go to stderr.

- [ ] **Step 3: Implement decision and transition rules**

`Gate` recomputes a fingerprint for a recorded pass. A mismatch atomically turns
that verification state into `stale`. It returns:

```go
Result{VerificationState: VerificationPassed, WorkflowState: WorkflowComplete, ReasonCode: "satisfied"}
```

for current evidence and no follow-up. For active unsatisfied state with a new
`LastRunID`, increment `RepairCount`, record `LastGateRunID`, and return one
short `FollowUp` that includes the reason code, run directory, and next command.
For the same run ID return no follow-up. On the fourth distinct decision set
`WorkflowBlocked` and return no follow-up.

`Resume` rejects a non-blocked/non-cancelled task, restores `WorkflowActive`,
sets `RepairCount` to zero, preserves the original baseline and verification
result, and records the resume timestamp. Add `gate` and `resume` CLI commands
and map gate exits exactly: 0 complete/not-applicable; 1 failed; 2
pending/stale/blocked/cancelled; 3 setup/internal.
